# UE
硬引用 vs 软引用 

## 一、概念区别（一句话人话版）

| 类型 | 人话解释 | 内存态度 | 使用代价 |
|------|----------|----------|----------|
| **硬引用** | 死死拽着资源不松手 | 资源常驻内存，绝不释放 | 快，但费内存 |
| **软引用** | 只记了个硬盘路径，没真拽着 | 资源在硬盘待着，随时可被回收 | 省内存，但用时要加载（可能卡） |

---

## 二、优缺点对比

### 硬引用（Hard Reference）
- **优点**：用的时候百分百存在，直接调用，无额外加载开销，代码简单省心。
- **缺点**：资源长期霸占内存，即使暂时不用也不会释放，容易导致内存浪费和加载卡顿。
- **适用场景**：角色基础模型、动画蓝图、常用音效、UI必备组件等**核心必需品**。

### 软引用（Soft Reference）
- **优点**：内存占用极低，资源按需加载，内存紧张时自动释放，降低内存峰值。
- **缺点**：使用时可能不在内存中，需手动加载（可能卡顿），且必须做判空处理，逻辑复杂。
- **适用场景**：超大贴图、CG视频、备用皮肤、结算界面特效等**偶尔用的大块头**。

## 三、软引用加载优化方案（如何不卡）

> 物理定律无法打破（硬盘读取需要时间），但可以通过策略让玩家**几乎感觉不到卡**。

### 方案1：预加载（最推荐，基本无感）
提前几秒在后台偷偷加载，等真正使用时资源已在内存中。

- **实现**：`FStreamableManager::RequestAsyncLoad` 提前发起异步请求。
- **适用**：可预测行为（如走向传送门、切换关卡）。

### 方案2：异步加载 + 转圈UI（最稳妥）
加载时立即显示加载提示，让玩家知道程序在响应，避免界面冻住带来的糟糕体验。

- **实现**：点击触发 → 显示转圈UI → 后台异步加载 → 加载完成隐藏UI并显示内容。
- **适用**：手动触发的加载场景（如打开仓库、查看皮肤）。

### 方案3：分帧加载（Chunk Loading）
将大资源拆分成小块，每帧只加载一部分，让卡顿分散到多帧，人眼无法感知。

- **实现**：使用 `AsyncLoading` 配合时间片控制，每帧处理固定数量的子对象。
- **适用**：大型场景加载、多组件同时出现的场合。

### 方案4：对象池（终极偷懒）
高频使用的资源（子弹、怪物）首次加载后永不释放，放池子里循环复用。

- **实现**：加载一次 → 存入池中 → 使用时直接取出（硬引用状态）。
- **适用**：频繁创建销毁的对象，用内存换流畅。
